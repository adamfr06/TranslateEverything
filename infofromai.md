## 2. Data flow

Game text is intercepted by a mixin. `CaptureManager` or `ChatTranslator` decides whether it is
worth translating. `TranslationService.translate` answers from the cache or dispatches to an
engine through `fetch`. The result is either swapped in place (`ImmersionService`) or shown as a
card (`BoxManager` to `HudLayout` to `TranslationHud`). Text the player types goes the other
way through `InputTranslator`, which shows a live preview and can open the review screen.

## 3. Decisions and measurements

Measurements were taken against OpenRouter (`deepseek/deepseek-v4-flash-0731` unless stated).

**Reasoning is disabled on OpenRouter.** Reasoning models spend billed output tokens thinking
before they answer. One 27-word chat line: reasoning on took 3578 ms and 563 completion tokens
for a 38-token answer; off took 645 ms and 38 tokens. When the thinking exceeded `max_tokens`
the reply was empty, which surfaced as "ran out of tokens before answering". Controlled by
`TEConfig.aiAllowReasoning` (default off).

**Compressed prompt.** The translation prompt was rewritten as numbered rules: 317 to 162
prompt tokens per call with identical accuracy (12/12 on the same test set).

**Chinese instructions are opt-in.** Chinese twins of the prompts measured slightly more
expensive, not less: 176 vs 162 prompt tokens (deepseek) and 194 vs 173 (qwen3-30b), same
accuracy. Kept as `aiPromptChinese` because results vary by model. The option covers the
translation prompt and the review/follow-up coach; replies stay in the player's language.

**No text substitution before translation.** An earlier version replaced bare greetings with a
fixed English sentence before any engine saw them, so "whats up" was sent as "hey, how's it
going?" and came back with a greeting word the player never typed. It also made conversation
context irrelevant. Removed.

**Casual openers get one targeted hint.** Without help, Japanese renders "whats up" as a bare
"やあ" (0/6). A general always-on rule helped only 3/6; a conditional length-based rule 2/6.
Stating the fact about the specific message ("contains no greeting word") scored 6/6 in
Japanese, Spanish and German with and without context. Thanks, apologies, farewells and
morning greetings were already correct without any hint, so the list is limited to the
"what's up" family (`CASUAL_OPENERS`).

**Same-language skipping.** `LanguageGuess` identifies scripts outright and scores 18
Latin-script languages by function words weighted by rarity. It only claims a language when
confident; an unsure answer means "translate it". Danish and Norwegian are treated as one.
Skipped chat lines carry a `⇄` that translates them on demand (`/teforce <id>`).

**Cache keys carry behaviour.** Every key includes `BEHAVIOUR_VERSION`, the model and a
fingerprint of the prompt. Without that, a prompt fix never applies to phrases already cached.
A translation approved on the review screen replaces every cached entry for that source text.

**Cards draw above open screens.** Minecraft renders world, then HUD, then the open screen, so
a card registered only as a HUD element sat underneath book, sign and inventory screens and
their dimming. `TranslationHud.renderOverScreen` draws the cards after the screen.

**Warm-up only for local models.** The periodic warm-up request keeps a local Ollama model in
memory. Against a hosted API it was a billed request every four minutes, so it is skipped.

**Whispers keep their envelope.** `CommandShape` preserves `/msg Name ` byte for byte and
translates only the message; unrecognised commands are never touched.

## 4. Known limitations

- `<<hints>>` reach the AI engine only; Google, Azure and LibreTranslate ignore them.
- The arbiter and faithfulness-check prompts are English only (not covered by `aiPromptChinese`).
- `MinecraftGlossary` matches English game terms in the source text, so glossary hints only
  help when translating from English.
- `looksAlreadyIn` has an extra English-only fallback word list for short server lines.
- `CASUAL_OPENERS` lists English phrases (outgoing messages written in English).
- `26.1.2/` has none of the 2.0+ work.

## 5. Working on the code

```bash
cd 26.2
./gradlew compileJava -q --offline     # compile check
./gradlew build --offline              # jar in build/libs/
touch run/te-shots && ./gradlew runClient --offline   # dev-only harness
rm -f run/te-shots
```

The harness (`ScreenShotHarness`, `GuiRegression`, `RenderingRegression`) runs only in a
development environment with a `te-shots` file in `run/`. It opens every screen, writes a
screenshot of each, audits every label against the real font for overflow, runs logic checks
(whisper parsing, sign widths, book colour) and verifies every mixin class is listed in the
mixin config. A mixin missing from that file fails at the call site rather than at startup,
which is how the 1.21.8 chat-send crash happened.

Bump `TranslationService.BEHAVIOUR_VERSION` whenever prompts or translation behaviour change.

### `dev/adamfr06/translateeverything/capture/ChatTranslator.java`

**Before** `public final class ChatTranslator {`

The chat translator. Three presentation modes (Settings > Chat):

REPLACE — the translated line replaces the original in chat. Hovering shows
the original; clicking copies the original; a dim ⧉ at the end copies the
translation.

BELOW — the original shows as normal with a translated line right under it.
Clicking the original copies the original; clicking the translation copies

configurable timeout passes) and release strictly in order, so chat never
reshuffles. Cached translations release instantly.

<h2>Echo guard</h2>
Because REPLACE/BELOW re-inject their result into the chat HUD, and other
chat mods (notably GoogleChat) re-dispatch chat lines asynchronously on a
worker thread, a simple "am I adding right now" flag isn't enough to stop
the mod from re-translating its own output — the re-entry arrives on a later
tick when that flag has already reset, causing an infinite translate loop.
So every line we emit is fingerprinted for a while; any incoming line whose
text matches a recent emission is recognised as our own echo and passed
straight through untouched. This makes re-ingestion impossible regardless of
threading or which other mod handed the line back.

### `dev/adamfr06/translateeverything/config/TEConfig.java`

**Before** `public class TEConfig {`

All user-tunable settings. Serialized as pretty JSON to
`config/translateeverything.json`. Every field has a sane default so a
missing / partial file always loads cleanly.

**Before** `public String azureKey = "";`

Azure Translator. The free tier covers 2M characters a month, which is far
more than chat uses, and it is not rate-limited the way the free Google
endpoint is. Needs the key and the region shown on the resource's Keys and
Endpoint page ("Global" works for most accounts).

**Before** `public String aiProviderSort = "throughput";`

OpenRouter picks a provider by price by default, which routes to the cheapest
host rather than the quickest one. "throughput" or "latency" makes it prefer
fast providers instead; "" leaves routing alone. Only sent to OpenRouter.

**Before** `public int aiMaxTokens = 2048;`

CEILING on generated tokens, not the value used. The real budget scales with
the message (see tokenBudgetFor), so a two-word chat line stays tightly bounded
while a full book page still fits. Measured: 968 characters of English needed
265 completion tokens in Japanese, and the input limit is 1500 by default, so
the ceiling has to be comfortably above that.

**Before** `public boolean aiAllowReasoning = false;`

Let a reasoning model think before it answers. Off, because translation is not
a reasoning task and the thinking is billed as output: measured on OpenRouter
with deepseek-v4-flash, one chat line cost 563 completion tokens and 3.6s with
thinking on against 38 tokens and 0.6s with it off, same translation. Worse,
long thinking eats the whole budget and the reply comes back empty, which is
the "ran out of tokens before answering" players were seeing. Turn it on only
to compare. Sent to OpenRouter; other endpoints ignore it.

**Before** `public boolean aiPromptChinese = false;`

Experimental: send the AI's instructions in Chinese. The theory is that a
Chinese-trained model reads its own language in fewer tokens. Measured on
OpenRouter it does not: 176 prompt tokens against 162 for the English rules on
deepseek-v4-flash, and 194 against 173 on qwen3-30b, with identical accuracy
(12/12 on the same suite either way). Output language is unaffected — the
player never sees Chinese. Left in so it can be re-checked on a new model.

**Before** `public String aiModel = "qwen2.5:3b";`

Model name the endpoint should use. Pick something small & fast (target: <2s).

**Before** `public String speakerTone = "";`

Speaker style/tone injected into the AI prompt. Blank = neutral.

**Before** `public String aiSystemPrompt = "";`

Custom AI system prompt. Blank = use the built-in default. {target} is
replaced with the target language name at request time; the tone and
context-hint lines are still appended automatically.

**Before** `public int aiTimeoutMs = 30000;`

AI request timeout (ms). Generous on purpose: the AI call runs on a

**Before** `private static String ensureHomeLanguage(String s) {`

Guarantee a model-written status line reaches the player in THEIR language,
whatever language the model actually answered in. Small models drift into the
target language constantly, and no prompt reliably stops it. Google detects the
language for us: if it isn't the player's, show a translation instead. One fast
HTTP round-trip; returns the input untouched on any failure.
